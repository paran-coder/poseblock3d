# 컨텍스트 노트

작업 중 내린 결정과 그 이유를 계속 이어서 기록합니다. 다음 세션에서 이 파일만 읽어도 이어서 작업할 수 있어야 합니다.

## 프로젝트 배경
- AI 영상 제작에서 화면 구성을 프롬프트로 설명하기 어려워하는 사람들이 많습니다.
- 지금은 2D 스케치를 레퍼런스로 쓰는데, 카메라 각도와 구도를 나중에 다시 손봐야 합니다.
- 3D 포즈 블로킹 도구로 구도와 카메라 앵글을 한 번에 잡는 것이 목표입니다.

## 결정 기록

### 결정 1. 관절은 24개로 간다
- 구성은 몸통과 머리 6, 팔 8, 손끝 2, 다리 8입니다.
- 사용자가 "구체를 조절하는 24개 관절"을 기준으로 알고 있었고, 이 구성에 동의했습니다.
- 손가락은 넣지 않습니다. 조작이 복잡해지고 구도 레퍼런스에는 불필요합니다.

### 결정 2. 손목과 발목은 IK, 나머지는 FK
- 드래그로 위치를 옮기면 뼈 길이가 늘어나기 쉬워서 IK가 필요합니다.
- 모든 관절을 IK로 하면 오히려 조작이 어려워집니다.
- 그래서 끝단(손목, 발목)만 IK, 나머지는 회전 링으로 다룹니다.

### 결정 3. 회전 컨트롤은 구가 아니라 3개 링
- 사용자는 처음에 "컨트롤 구 형태"를 말했습니다.
- 구 하나로 3축을 다루면 정밀하지 않아서 빨강·초록·파랑 링을 제안했고, 큰 방향은 동의를 받았습니다.
- 구 형태의 시각적 느낌은 링을 구 모양으로 배치해서 살립니다.

### 결정 4. 웹 기반, 단일 HTML, Three.js
- 설치 없이 바로 열 수 있고 공유가 쉽습니다.
- 클립보드 이미지 복사는 HTTPS 또는 localhost에서만 되므로, 실패 시 PNG 다운로드로 대체합니다.

### 결정 5. 캡처는 메인 화면만
- 렌더러 캔버스만 읽어서 UI가 섞이지 않게 합니다.
- 캡처 순간 기즈모, 그리드, 라벨을 숨기는 옵션을 둡니다.
- 깜박임은 화면 위에 흰색 오버레이를 짧게 보여 주는 방식으로 처리합니다.

### 결정 6. 범위는 단계적으로
- 1차는 캐릭터 조작, 카메라, 캡처, 포즈 저장까지입니다.
- 프리셋 포즈, 대칭, 소품, 실루엣 내보내기는 2차로 미룹니다.
- 프리셋 포즈는 사용 빈도가 높을 것으로 예상해 2차 최우선입니다.

### 결정 7. 포즈 저장을 1차에 포함한다
- 사용자가 이전에 쓴 포즈를 바로 재사용하는 기능을 제안했고, 반복 사용이 많을 것이라 1차로 올렸습니다.
- 저장 단위는 포즈(관절 회전값만)와 씬(캐릭터, 카메라, 화면비 전체) 두 가지입니다.
- 포즈에 위치와 키를 넣지 않는 이유는 어떤 캐릭터에도 적용할 수 있게 하기 위해서입니다.
- 썸네일을 같이 저장해 목록에서 그림으로 고르게 합니다.
- localStorage와 JSON 내보내기를 병행합니다. localStorage는 Claude 미리보기에서 막혀 있어 로컬 파일 실행을 기본으로 합니다.

### 결정 8. 캐릭터는 선과 구에 반투명 몸통을 더한다
- 관절 조작이 잘 보이도록 뼈(선)와 관절 구를 기본으로 하고, 영상 AI가 부피를 인식하도록 반투명 몸통을 켜고 끌 수 있게 했습니다.
- 몸통과 관절 구 표시 설정은 화면과 캡처 결과에 똑같이 적용됩니다.
- 머리에는 코(작은 원뿔)를 달아 캐릭터가 어느 쪽을 보는지 알 수 있게 했습니다.

### 결정 9. 관절 드래그 방식
- 손목과 발목은 2본 해석적 IK입니다. 끌어도 손과 발의 방향이 유지됩니다.
- 그 외 관절은 "잡은 관절이 커서를 따라오도록 부모 관절을 회전"시키는 방식입니다. 뼈 길이가 늘어나지 않습니다.
- 골반을 끌면 캐릭터가 이동하고, Shift를 누르면 위아래로 움직입니다. 점프 구도를 잡을 때 씁니다.
- 쇄골과 엉덩이는 끌어도 움직이지 않고 선택만 됩니다. 링으로 회전합니다. 부모가 몸 전체라서 끌기를 넣으면 오히려 조작이 어색해집니다.
- 알려진 특성 하나. 하부 척추를 끌면 골반이 회전해 몸 전체가 기웁니다. 의도된 동작이지만 처음엔 놀랄 수 있습니다.

### 결정 10. 회전 링은 화면 접선 방식으로 구현
- 링 평면과 마우스 광선의 교차를 쓰면 링이 옆면으로 보일 때 조작이 안 됩니다.
- 그래서 링 위 점의 접선 방향을 화면에 투영해 마우스 이동량을 회전각으로 바꿉니다. 어느 각도에서 봐도 동작합니다.
- 링의 축은 캐릭터 방향을 따라갑니다.

### 결정 11. 출력 카메라와 작업 카메라를 분리
- 작업 뷰는 자유 시점이고, 출력 카메라는 주황색 상자로 보입니다. 왼쪽 아래 작은 창에서 출력 화면을 미리 볼 수 있습니다.
- 카메라 뷰에서는 출력 화면비 그대로 프레임이 표시되고 바깥은 어둡게 처리됩니다. 3분할선도 표시합니다.
- "현재 작업 뷰 시점을 출력 카메라로" 버튼으로 마음에 드는 시점을 바로 가져올 수 있습니다.

### 결정 12. 캡처는 별도 렌더러로 만든다
- 화면에 보이는 캔버스를 복사하지 않고, 보이지 않는 렌더러로 긴 변 1920px 이미지를 새로 그립니다. 창 크기와 상관없이 같은 해상도가 나옵니다.
- 회전 링, 바닥 원, 카메라 상자, 이름표는 캡처에 들어가지 않습니다. 그리드는 옵션입니다.
- 클립보드 복사에 실패하면 자동으로 PNG를 내려받게 합니다.

### 결정 13. 단일 index.html과 의존성 (결정 24로 구조 변경)
- Three.js r128을 cdnjs에서 불러오고, 카메라 조작과 회전 링은 직접 구현했습니다. 별도 빌드가 필요 없어 Vercel에 그대로 올릴 수 있습니다.
- 현재 상태를 자동 저장(autosave)해서 새로고침해도 이어서 작업할 수 있습니다. 포즈와 씬 목록은 localStorage에 저장하고, JSON 내보내기를 백업용으로 둡니다.

### 결정 14. OG 이미지 태그
- `og-image.png`(1200x630) 태그를 미리 넣어 두었습니다. 파일은 아직 없습니다.
- 현재는 상대 경로입니다. 일부 SNS 크롤러는 절대 주소만 인식하므로, 도메인이 정해지면 `https://도메인/og-image.png`로 바꿔야 합니다.

### 결정 15. 패널을 좌우로 나눈다
- 저장물이 늘어나도 설정 패널이 길어지지 않도록, 왼쪽은 설정(캐릭터, 소품, 카메라, 보기 탭)과 오른쪽은 라이브러리(프리셋, 내 포즈, 씬 탭)로 분리했습니다.
- 왼쪽 설정 패널은 어느 탭에서도 스크롤 없이 한 화면에 들어옵니다.
- 화면 폭이 1100px 이하이면 3D 화면 아래로 설정, 라이브러리 순서로 쌓입니다.
- 사용자가 제안한 두 방식(탭 구분, 좌우 분리)을 함께 적용한 구성입니다.

### 결정 16. 자세 프리셋은 관절 각도 표로 관리한다
- 각도(도 단위, 오일러 XYZ)로 정의하고, 좌우 대칭 자세는 왼쪽만 쓰면 오른쪽이 자동으로 반전됩니다.
- 팔짱처럼 손 위치가 중요한 자세는 각도 위에 손목 IK 목표 좌표를 얹어 만들었습니다.
- 프리셋은 포즈 저장과 같은 방식으로 관절 회전값만 바꿉니다. 캐릭터의 위치, 키, 방향은 그대로입니다.
- 적용 후에는 발이 바닥에 닿도록 높이를 자동으로 맞춥니다. 앉기는 약 0.42m 내려가고, 점프는 0.4m 위에 뜹니다.
- 이를 위해 캐릭터 높이 허용 범위를 -1.2m~3m로 넓혔습니다.
- 내 포즈를 적용할 때는 캐릭터가 바닥에 서 있던 경우에만 다시 바닥에 맞춥니다. 점프 중이던 캐릭터는 그대로 둡니다.
- 프리셋 썸네일은 3/4 각도로 앱이 직접 그립니다. 별도 이미지 파일이 없습니다.

### 결정 17. 카메라 위치 이동 방식 4가지
- 카메라 탭 슬라이더(좌우, 높이, 앞뒤)는 방향은 그대로 두고 위치만 옮깁니다.
- 작업 뷰에서 주황색 카메라를 직접 끌면 수평으로 이동하고, Shift를 누르면 높이만 바뀝니다.
- 카메라 뷰에서는 W A S D로 앞뒤좌우, Q E로 아래위로 이동합니다. Shift는 큰 걸음입니다.
- 카메라 본체와 캐릭터 관절이 화면에서 겹치면 더 가까운 쪽이 잡힙니다.
- 기본 작업 시점은 캐릭터를 앞쪽 3/4에서 보는 큰 화면입니다. 이때 출력 카메라가 화면 밖일 수 있어 "출력 카메라 찾기" 버튼을 두었습니다.
- 시험해 보니 캐릭터를 옆에서 보면 좌우 팔이 겹쳐 엉뚱한 관절이 잡혔습니다. 기본 시점으로 옆모습을 쓰지 않는 이유입니다.

### 결정 18. WebGL 컨텍스트는 하나만 쓴다
- 캡처와 썸네일은 보이지 않는 별도 렌더러 대신, 메인 렌더러의 오프스크린 렌더 타깃에 그린 뒤 픽셀을 읽어 2D 캔버스로 옮깁니다.
- 컨텍스트 중복이 없어 메모리를 덜 쓰고, 브라우저의 컨텍스트 개수 제한과도 무관합니다.
- 멀티샘플 렌더 타깃(WebGL2)으로 가장자리 계단 현상을 줄이고, WebGL2가 없으면 일반 렌더 타깃으로 대체합니다.

### 결정 19. 카메라는 "위치"와 "방향"을 따로 다룬다
- 처음에는 출력 카메라를 대상 둘레로 도는 궤도 회전만 있어서, 카메라가 바라보는 방향을 바꿀 수 없다는 지적이 있었습니다. 위치 이동을 만든 뒤에도 방향 조절 수단이 빠져 있었습니다.
- 이제 방향은 좌우(요), 상하(피치), 기울기(롤) 세 축으로 직접 조절합니다. 조절해도 카메라 위치는 변하지 않습니다.
- 카메라 뷰에서 드래그하면 기본적으로 제자리 회전입니다. 장면을 잡아 끄는 느낌이라 오른쪽으로 끌면 장면이 오른쪽으로 밀립니다. Alt를 누르면 대상 중심 회전이 되고, 카메라 탭에서 기본 방식을 반대로 바꿀 수 있습니다.
- 작업 뷰에서는 주황 카메라 앞에 조준점(작은 구)이 있어 끌면 방향이 바뀝니다. 조준점과 카메라 본체, 관절이 겹치면 화면에서 가까운 것이 잡힙니다.
- 로우앵글, 아이레벨 같은 앵글 프리셋은 대상을 바라본 채 높이만 바꾸는 기존 동작을 유지합니다.
- 롤은 시선 방향과 독립이라 방향 슬라이더에 영향을 주지 않으며, 최대 ±45°입니다.

### 작업 중 얻은 교훈 (추가)
- 렌더 루프는 스크립트 중간에서 시작되므로, 렌더 중 호출되는 코드가 쓰는 상수는 반드시 스크립트 상단에서 선언해야 합니다. 뒤쪽에 선언한 상수를 참조해 접근 에러가 난 적이 있어, `D2R`와 `wrap180`을 상단으로 옮겼습니다.

### 작업 중 얻은 교훈
- 패널 재구성 중 3D 화면 블록이 문서에 두 번 들어간 실수가 있었습니다. 빈 화면이 위에 덮여 3D 화면이 검게 보였고, 요소 목록을 직접 조회해서 찾았습니다.
- 구조를 바꾼 뒤에는 `#stage`와 `canvas`가 정확히 하나인지부터 확인합니다. 테스트에 이 검사를 넣어 두었습니다.

### 결정 20. 두 회전 방식을 확실히 구분한다 (결정 19 수정)
- 사용자가 "제자리 회전과 대상 중심 회전이 똑같이 보인다"고 지적했습니다. 재현해 보니 원인이 두 가지였습니다.
  - 전환 버튼이 카메라 탭 안에 있었고 카메라 뷰에서만 적용되어, 작업 뷰에서 시험하면 두 방식의 결과가 완전히 같았습니다.
  - "대상 중심"의 중심이 캐릭터가 아니라 카메라 내부의 보이지 않는 조준점이었습니다. 제자리 회전을 한 번 하면 이 조준점이 빈 공간으로 밀려나, 이후 "대상 중심 회전"이 허공을 축으로 돌았습니다.
- 수정 내용은 다음과 같습니다.
  - 회전 중심은 선택한 캐릭터의 가슴 높이입니다. 선택이 없으면 모든 캐릭터의 중앙입니다.
  - 대상 중심 회전은 카메라를 통째로 돌립니다(강체 회전). 캐릭터까지의 거리, 화면 속 캐릭터 위치가 그대로 유지됩니다.
  - 제자리 회전은 카메라 위치를 고정하고 방향만 바꿉니다.
  - 전환 버튼은 3D 화면 오른쪽 위에 두고 작업 뷰와 카메라 뷰 모두에 적용합니다. 방식은 뷰마다 따로 기억합니다. 작업 뷰는 편집용이라 대상 중심, 카메라 뷰는 구도용이라 제자리가 기본입니다.
  - 화면 상단 안내 칩에 현재 방식을 표시하고, 대상 중심 회전 중에는 회전 중심에 노란 십자를 잠깐 보여 줍니다.
  - 앵글 프리셋(로우앵글, 아이레벨, 하이앵글, 버즈아이)도 같은 이유로 선택 캐릭터를 바라보며 같은 거리에서 높이만 바꾸도록 고쳤습니다.
- 카메라 탭의 전환 버튼은 삭제하고, 위치를 알려 주는 안내 문구만 남겼습니다.

### 작업 중 얻은 교훈 (추가 2)

### 결정 21. 방향은 "발이 향하는 쪽"을 기준으로 보여 준다
- 사용자가 "캐릭터를 마주보게 했는데 파란 캐릭터 아래 방향은 그대로"라고 지적했습니다. 상체만 비튼 경우와, 몸을 돌려도 바닥 화살표가 그대로인 경우 두 가지로 읽혀서 둘 다 대응했습니다.
- 바닥 화살표는 이제 두 발이 향하는 방향을 가리킵니다. 골반 링, 하체 정렬, 프리셋 등으로 몸이 돌아가면 화살표도 따라갑니다. 발끝이 거의 수직이면 골반 방향으로 대신합니다.
- 화살표를 끌면 캐릭터 전체가 돌아갑니다. 상체와 하체가 함께 회전합니다.
- "하체 방향을 상체에 맞추기"는 두 엉덩이 관절만 월드 수직축으로 돌립니다. 상체, 머리, 팔은 한 치도 움직이지 않습니다(위치 오차 1e-6 이하).
- "상대 바라보기"와 "서로 마주보기"는 상체가 상대를 향하도록 캐릭터 전체를 돌린 뒤 하체도 같은 방향으로 맞춥니다. 위치, 키, 자세는 그대로이고 사선 배치와 앉은 자세에서도 오차가 0.3° 이하입니다.

### 결정 22. 소품은 단순한 도형 조합 10종

- 가로·높이·세로를 따로 늘일 수 있고 "비율 유지"가 기본 켜짐입니다. 크기는 20~400%입니다.
- 소품은 캐릭터 조작을 방해하지 않습니다. 같은 자리에서 클릭하면 관절, 화살표, 바닥 원 다음에 소품이 선택됩니다. 소품이 캐릭터를 가려 조작하기 어려우면 "소품 반투명" 옵션을 씁니다.

- 소품은 최대 30개입니다. 선택 윤곽선은 에디터 보조물이라 캡처에 나오지 않습니다(선택/비선택 캡처가 픽셀 단위로 동일함을 확인).

### 결정 23. 공유는 링크와 파일 두 가지

- 받는 사람이 링크를 열면 포즈는 "내 포즈"에 자동 추가됩니다. 씬은 바로 덮어쓰지 않고 확인 창을 먼저 띄웁니다. 열면 기존 작업은 "공유 링크 열기 전 작업"으로 자동 보관됩니다.

- 로컬 파일로 연 상태에서 만든 링크는 그 컴퓨터에서만 열리므로, 공유 창에 이 사실과 "파일로 저장" 대안을 안내합니다. Vercel 등 웹 주소에서 만든 링크는 누구나 열 수 있습니다.
- 파일 내보내기는 기존 JSON 형식을 그대로 쓰되 항목 하나만 담습니다. 받는 사람은 기존 "JSON 가져오기"로 불러옵니다. 파일 이름은 영문·숫자로 만들고 실제 이름은 파일 안에 담습니다(일부 환경에서 한글 파일명이 깨지는 문제를 확인했기 때문입니다).
- 라이브러리 카드마다 "공유 · 내보내기" 버튼이 있고, 저장하지 않은 현재 상태는 "저장 없이 공유"와 헤더의 "공유"로 바로 보냅니다.

### 결정 24. 배포용은 파일을 나누고, 확인용 단일 파일은 빌드로 만든다
- 사용자는 처음부터 "최종적으로는 GitHub에 올려 Vercel로 배포하고, 단일 HTML은 작업 중 확인용"이라고 했습니다. 이 구분을 놓치고 단일 파일을 그대로 압축해 전달했다가 지적을 받았습니다.
- 단일 파일도 정적 사이트라 Vercel에 그대로 배포되지만, 정식 저장소 구조로 정리했습니다.
  - `index.html`은 뼈대, 메타 태그, OG 태그만 남깁니다. 스타일은 `css/style.css`, 로직은 `js/app.js`로 옮겼습니다.
  - 내용은 한 글자도 바꾸지 않고 위치만 옮겼습니다. 단일 빌드본의 CSS와 JS 본문이 이전 단일 파일과 동일함을 대조해 확인했습니다.
- JS는 더 잘게 나누지 않았습니다. 앱 전체가 하나의 클로저 안에서 상태를 공유하고, 함수 선언의 호이스팅에 기대는 부분이 있어서, 모듈로 쪼개면 동작이 바뀔 위험이 큽니다. 기능이 더 커지면 그때 모듈화를 검토합니다.
- 확인용 단일 파일은 `node scripts/build-single.mjs`로 `dist/poseblock-single.html`을 만듭니다. `dist/`는 `.gitignore`에 넣어 저장소에는 올리지 않습니다. Node.js 18 이상이면 되고 패키지 설치가 필요 없습니다.
- 분리본은 `file://`로 열어도 동작합니다. 일반 스크립트(모듈 아님)와 상대 경로만 쓰기 때문입니다.
- Three.js는 계속 CDN(cdnjs)에서 불러옵니다. 오프라인 사용이나 CDN 의존을 없애고 싶다면 `js/vendor/`에 내려받아 넣는 방법이 있습니다(약 600KB).

### 작업 중 얻은 교훈 (추가 3)
